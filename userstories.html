02 — User Stories & Tasks

GoShuttle features written from the student and driver perspective, broken down into concrete development tasks per sprint.

Evidence — GoShuttle User Stories & Tasks

Each story follows the format: "As a [user], I want to [action] so that [benefit]." Stories are grouped by persona and linked to ERD packages and sprint assignments.

👤 Persona: CPUT Commuter Student

US-01  |  Package 1 — Campus & User  |  Done
"As a CPUT student, I want to register an account with my student number and home campus so that I can access personalised shuttle information."
  • Create User table on Supabase with StudentNumber, Email, PasswordHash, CampusID (FK)
  • Build RegisterView.vue form with input validation (email format, student number length)
  • Insert new user record into Supabase on form submit
  • Fix campus_id FK mismatch between select value and numeric foreign key
  • Display success/error feedback message after registration attempt
US-02  |  Package 1 — Campus & User  |  Done
"As a CPUT student, I want to select my home campus during registration so that the app shows me only relevant routes."
  • Seed Campus table with 5 CPUT campuses (Bellville, Cape Town, District Six, Mowbray, Wellington)
  • Fetch campus list from Supabase and populate dropdown in RegisterView.vue
  • Store selected campus_id as FK on User record
US-03  |  Package 2 — Routes & Stops  |  Done
"As a CPUT student, I want to see all available shuttle routes so that I can choose the one closest to my home area."
  • Create Route table with RouteCode, OriginArea, DestinationCampusID, TotalStops, EstimatedDuration, FrequencyMinutes
  • Seed routes G1 (Khayelitsha), G2 (Mitchells Plain), G3 (Kraaifontein)
  • Build route-selector UI component that reads from Supabase
  • Display route cards with departure times and estimated journey duration
US-04  |  Package 2 — Routes & Stops  |  Done
"As a CPUT student, I want to see the ordered stops along my route so that I know where to wait and when the bus will arrive."
  • Create Stop table with RouteID (FK), StopName, AreaName, SequenceOrder, OffsetMinutes, IsCampusStop
  • Seed stops for G1, G2, G3 in correct SequenceOrder
  • Display stop timeline in the frontend using OffsetMinutes to calculate ETAs
  • Highlight campus stop with a distinct visual marker (IsCampusStop = true)
US-05  |  Package 3 — Fleet & LiveTrip  |  Done
"As a CPUT student, I want to see a live map showing where my bus is right now so that I know exactly when to leave my house."
  • Create LiveTrip table with BusID, RouteID, CurrentStopID, latitude, longitude, Status, ArrivesInMinutes, ToCampusMinutes, updated_at
  • Build TrackView.vue with Leaflet map integration
  • Poll Supabase for LiveTrip updates every 10 seconds
  • Draw route line on map using Stop coordinates
  • Show bus icon at current lat/lng position
US-06  |  Package 4 — Pass & Integration  |  In Progress
"As a CPUT student, I want to view my shuttle pass details so that I know how many trips I have left and how much I have saved."
  • Create Pass table with UserID (FK), PassType, ValidUntil, DaysLeft, TripsUsed, AmountSaved, PreferredRouteID (FK)
  • Build PassService to calculate DaysLeft and AmountSaved dynamically
  • Build My Pass page displaying pass metrics in dashboard cards
  • Wire PreferredRoute selector to Pass table update

🚌 Persona: GoShuttle Driver

US-07  |  Package 3 — Fleet & LiveTrip  |  Done
"As a GoShuttle driver, I want to share my GPS location so that students can see where my bus is in real time."
  • Create Driver table with DriverName; Bus table with BusNumber, RouteID (FK), DriverID (FK), Capacity, CapacityPercent
  • Build DriverTrack.vue with navigator.geolocation.watchPosition for live GPS tracking
  • Add manual coordinate entry form as fallback for unreliable GPS in demo environments
  • Upsert LiveTrip record on Supabase with latest lat/lng and updated_at on each GPS update
  • Add unique constraint on bus_id in live_trip table to support upsert operations
Reflection — What I Learned from Writing User Stories

Writing user stories for GoShuttle fundamentally changed how I approached backend development. Before this project, I would start by designing database tables and then work outward. User stories forced me to start with the person — what does Thabo, the Khayelitsha student, actually need to do? — and then trace backwards to what the system must support.

The most valuable lesson came from US-01 (student registration). I wrote the story, listed the tasks, and only then discovered that the campus_id FK mismatch would cause a silent insert failure. Because the task was framed around a user outcome ("register successfully"), I noticed the failure during testing rather than assuming the insert worked. Without the user story lens, I might have declared the task done at the point of writing the insert query.

I also learned to write stories at the right level of granularity. My first draft of US-04 was: "As a student I want to see my route." That is too vague to test. After refining it to include the ordered stops and OffsetMinutes ETA, the acceptance criteria became testable — I could seed data and verify that Stop 1 appears before Stop 2 on the map. This precision saved hours of rework in mid-August.

Going forward, I plan to write user stories before writing a single line of code on all my personal projects, including OweMe. The discipline of thinking as the user first — even on solo projects — produces better, more purposeful software.
