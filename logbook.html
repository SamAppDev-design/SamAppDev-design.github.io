Daily Standup Log — August 2026

1–5 August 2026 | Architecture Week
Sprint 2 Kickoff — Architecture Decision & Campus Foundation
Samukelisiwe: Confirmed GitHub Pages hosting limitation with the team. Led group discussion on backend alternatives. Team agreed to Supabase. Created Campus table on Supabase and seeded all 5 CPUT campuses (Bellville, Cape Town, District Six, Mowbray, Wellington). Trello board set up with all 20 sprint tasks.

Blocker resolved: Team almost started Spring Boot development before realising it cannot be hosted on GitHub Pages. Early discovery saved at least 2 weeks of wasted work.
6–10 August 2026 | Package 1
User Table, Registration Flow & FK Fix
Samukelisiwe: Designed User table linking to auth.users; simplified to prototype model. Built RegisterView.vue with form validation and Supabase insert. Discovered campus_id FK mismatch — select component was sending string value but DB expected numeric bigint. Fixed by explicit type conversion in the insert payload.

Blocker raised: UUID vs bigint type conflict in Row Level Security policies. Diagnosed, documented and resolved with explicit casting. Plaintext password trade-off documented as known limitation.

Package 1 status: ✅ Complete — Package 2 can begin.
11–15 August 2026 | Package 2
Routes, Stops & Scheduling (Sinethemba)
Sinethemba: Created Route table after Campus was confirmed live. Seeded G1 (Khayelitsha → Bellville), G2 (Mitchells Plain → CT), G3 (Kraaifontein → Bellville). Created Stop table with SequenceOrder and OffsetMinutes. Confirmed DepartureTime seeding approach in team standup before proceeding.

Samukelisiwe (Team Leader check-in): Verified all Route records have valid DestinationCampusID FK values matching the Campus table. Confirmed with Mvuyisi that Stop data was ready for LiveTrip FK references.

Package 2 status: ✅ Complete — Package 3 can begin.
16–20 August 2026 | Package 3 (Part 1)
Bus, Driver & LiveTrip Tables (Mvuyisi)
Mvuyisi: Created Bus table (BusNumber, RouteID FK, DriverID FK, Capacity, CapacityPercent) and Driver table. Attempted LiveTrip upsert — hit NOT NULL constraint on route_id and missing lat/lng/updated_at columns. Iteratively refined schema: added columns, added unique constraint on bus_id to support upsert operations.

Key learning flagged in standup: Schema gaps should be caught in design review before table creation, not during upsert testing. Action: Sprint 3 will include a schema design checklist.
21–25 August 2026 | Package 3 (Part 2) + Package 4 start
DriverTrack.vue, TrackView.vue Leaflet Map & Pass Table
Mvuyisi: Built DriverTrack.vue with dual input paths — navigator.geolocation.watchPosition for real GPS and manual coordinate form for demo environments where GPS permissions are unreliable. Updated TrackView.vue with Leaflet map that polls Supabase every 10 seconds and draws route line between stops.

Kwanda: Began Package 4 — created Pass table with UserID and PreferredRouteID foreign keys. Started PassService for DaysLeft, TripsUsed and AmountSaved metrics.

Team standup highlight: First time all 4 packages had active development simultaneously. Team morale was high — the live map was working and showing the bus moving on screen.
26–31 August 2026 | Integration & Sprint Close
Cross-Package Integration, Seed Consistency & Sprint Retrospective
Kwanda: Ran cross-package relationship verification — confirmed all FK chains resolve correctly: Pass → User → Campus; Pass → Route → Stop; LiveTrip → Bus → Driver. Seed data consistency check passed. Documented known limitations list and scaffolded README.

Samukelisiwe (Sprint Close): Confirmed registration → live tracking path is demo-ready end-to-end. Closed all completed Trello cards. Sprint velocity: 61 of 63 planned story points delivered (95%).

Known limitations documented: Hardcoded map origin coordinates; illustrative fares (not real); plaintext password storage in prototype.

Reflection — What I Learned from Keeping the Agile Logbook

Keeping the Agile logbook was the artefact I resisted most at the start of this project. It felt like writing a diary about code, which seemed unnecessary when the code itself was the evidence of progress. By the end of Sprint 2, I had completely reversed that view. The logbook became the most honest artefact we produced — not because it recorded our successes, but because it recorded our blockers, our decisions, and the moments when we had to change direction.

The entry for 6–10 August captures something that no other artefact shows: the fact that the campus_id FK mismatch caused a silent insert failure. Without the logbook, that problem — its diagnosis, its fix and its root cause — would have been lost. When Kwanda ran cross-package integration tests at the end of the sprint, he checked the logbook to understand what type casting had been applied to campus_id, which saved him from repeating the same investigation independently.

The retrospective section of the logbook was the most valuable for my development as a team leader. Writing "PassService was under-estimated" forces me to ask why — and the answer (that tasks spanning backend logic and frontend display are always underestimated) became a rule I will apply to every future sprint estimation. Retrospectives without a written record are just conversations that are forgotten; written retrospectives become institutional knowledge.

If I could improve our logbook, I would write standup entries daily rather than weekly. The weekly summaries lose granular details — on 18 August, for example, Mvuyisi found and fixed the LiveTrip NOT NULL constraint, but the exact error message and solution were not captured because the standup was summarised rather than logged in real time. In future projects I will use a simple shared Google Doc for daily standup entries, then transfer summaries to the formal logbook weekly.
